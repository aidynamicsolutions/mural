# Mural engineering

## Working approach

- Establish the requested outcome, affected data flow/callers, and invariants before editing. Clarify ambiguous outcomes or scope with the user; choose ordinary implementation details within the agreed constraints without asking the user to manage the work.
- Choose approach and depth from uncertainty, reach, and consequences, not model identity or diff size. These instructions constrain safety and evidence, not a fixed investigation sequence, reasoning level, or number of attempts. Operational deadlines and explicit device-authorization gates still apply.
- Load applicable skill entry points and consult references for questions relevant to the change. Reuse guidance still available and applicable in context; retrieve missing or changed guidance as needed. A reference link or incidental keyword is not a requirement to read every related document or expand the task into an audit.
- Prefer coherent patches and hypothesis-driven checks. After a surprising result, reassess the explanation and measurement before changing another parameter. Repeated work needs new evidence or an unresolved requirement, not merely another opportunity to run tools.
- Coordinate overlapping source edits and shared build resources as well as device ownership. Preserve unrelated changes, inspect unexpected concurrent changes before proceeding, and reassess temporary blockers before reporting them as current.

## Project verification

- Reuse the single persistent `Mural Lifecycle Verification` simulator, UDID `C094F154-7674-4A17-9F6B-319959B1F49A` (iPhone 17 / iOS 27.0), across tasks, retries and worktrees. If busy, wait; never create per-task/retry devices or parallel test-worker clones. Preserve its app/model data. Additional migration/runtime/screen-size devices require a concrete coverage gap, user approval and an agreed cleanup plan before creation; save evidence outside them, then delete only approved temporary devices after testing. If the primary is missing, inspect the inventory before deliberately replacing it.

- Simulator verification must use `active-ios-simulator-limit run -- make agent-verify SIM_UDID=<explicit owned Shutdown UUID>` (validated Mural slimming by default), or the enclosing `scripts/verify_simulator.py` for custom bounded flows. For known changes, use the smallest sufficient `TESTS='testMethod ...'` selection; it replaces rather than adds to smoke. Omit `TESTS` for the three-check smoke fallback; use `VERIFY_SUITE=qualification` for the broader 13-check profile/runtime acceptance. Routine runs share a ten-minute build/runtime/cleanup budget; a timeout or overrun is failure, never permission to cut off shutdown. See [the speedup plan](docs/simulator-test-speedup-plan.md).
- Use `SIMULATOR_MODE=stock` / `--stock` to restore managed services for affected integrations. SimSlim 0.11.0 is required; no silent fallback. `active-ios-simulator-limit run -- make build` only compiles and never boots. Gate the outer workflow, including prebuild, with the shared two-permit limiter; different simulator locks do not replace host admission. Never stop their workloads to improve timings.
- Never borrow a booted simulator, bypass the shared per-device/DerivedData locks, create parallel test workers, or leave owned devices running between tool calls. Require saved cleanup PASS and confirmed Shutdown on success, failure, timeout and cancellation. Detached mirrors need ownership-aware finalizers; preserve evidence and app/model data. Never target another project's resources or automatically run a physical-phone check.
- Simulator preview UI and synthetic setup checks do not prove real microphone, model, speech output or native background execution. Keep physical acceptance separate.

- Keep Xcode output concise: pipe `xcodebuild` through the installed `xcbeautify --is-ci`, with `set -o pipefail` and `tee` saving the raw log under `.build/verification/`. For test actions, set a unique `-resultBundlePath` and use `xcrun xcresulttool get test-results summary --path <bundle> --compact`; inspect only focused failure details. Never dump full logs or result bundles into agent context.
- For visual bugs involving animation, shifting, snapping, flicker, or transient clipping, follow [verify-mural's UI animation workflow](.agents/skills/verify-mural/features/ui-animation.md). Inspect the transition, not only the settled state. If recording or input is blocked, report that limitation explicitly; do not claim the animation was verified.

## Physical acceptance and efficient verification

- The real iPhone is the primary acceptance surface for microphone capture, actual ASR/tutor/TTS, audible output and native lifecycle behavior. Simulator previews support UI/guard checks, not those claims. Use the closest relevant surface, not compulsory duplicate simulator and phone suites.
- Physical testing remains explicitly opt-in through `make agent-verify-device`, separate from simulator targets. Follow [verify-mural's physical workflow](.agents/skills/verify-mural/SKILL.md#qualified-opt-in-native-local-workflow) and select the smallest sufficient stage. Initial or affected-contract requalification requires native/model readiness, one acoustic turn, then multi-turn/persistence; routine runs do not automatically repeat the whole ladder.
- Finish safe build/fixture preparation before requesting an audible window. Carry existing authorization forward; consolidate necessary unlock, permission, placement and listening actions. Keep mirroring closed during microphone tests; room-audio capture requires separate permission.
- Preserve the installed main bundle, intended signed build/backend, assets, caches, settings and personal history. Stop on model/resource faults or unsafe thermal conditions; never retry automatically, switch backends or delete apps to unblock provisioning without explicit authorization.
- Use saved Make/Python entrypoints and reports rather than recurring inline scripts. Runtime uses a copied, fingerprinted prepared `.xctestrun`, not project package resolution. Diagnose the first failure; qualify selector/cleanup repairs through a model-free regression before replaying expensive model scenarios. Reuse matching preparation/evidence only under the skill's identity rules.
- A preparation receipt is prior-success evidence, not ownership of Core ML's cache. Installation can relocate the data container without changing assets; preserve stable in-sandbox identity and all manifest/runtime/compute invalidation checks. A hit must still load and validate the model. Measure actual loading, not hypothetical savings from skipped prewarm.
- Save scoped evidence under `.build/verification/`, restore changed settings and stop all owned playback/capture/test processes. Separate automated assertions, human listening confirmation and unverified behavior. Physical cleanup never means shutting down the phone.
- Keep measured timing, qualified optimizations and remaining gaps in [physical E2E lessons](docs/physical-iphone-e2e-lessons.md). Compare identical coverage including cleanup, report build time separately when excluded, and never shorten readiness/safety gates merely to improve a number.

### Launch and failure-prevention checklist

- Immediately before a physical runtime stage, refresh `DEVICE_STAGE=status` after build/handoff delays. A user-confirmed idle phone does not imply Mural has no process. Resolve an existing process with the saved exact-PID `stop-idle` stage only under that idle authorization. If the PID disappears, confirm the fresh inventory is empty; do not keep retrying the stale PID. A new PID requires fresh matching-bundle verification and current idle authorization, never blind substitution. During an explicit exclusive test handoff, keep status, exact-PID stop and runtime adjacent to avoid stale state. Never weaken ownership checks to make Make return success.
- Read the run's `failure.json`, compact test summary and cleanup result before another command. Distinguish preflight refusal, build failure, app/runtime fault and interrupted host ownership. `make: Error` is not a diagnosis. Do not diagnose a UI symptom from a nearby source bug before inspecting the actual screen/log sequence.
- After a canceled tool call or lost host, treat cleanup as unconfirmed until saved cleanup and owned-process checks prove otherwise. Do not start another run over orphaned XCTest/console/profiler work. Record ownership-aware recovery separately; it never turns the interrupted original into a pass.
- For real download integrations, preserve literal observed redirect headers, including empty query values, encoding and quoted ETags. Regress those exact forms through the production HTTP path before a large phone transfer; hand-simplified URLs and a successful curl alone do not qualify the app's policy. Keep host/path/pin restrictions narrow and fail promptly on setup errors.
- When changing native compilation flags, inspect every affected enum case, UI switch, app entry point, bridge, generator and test contract before building. Use current qualified device APIs for screenshots; capture only the authorized app/surface, never use a screenshot of an unknown foreground app as a process-status check. See the [evidence-backed failure review](docs/physical-iphone-e2e-lessons.md#september-28-session-review-preventable-command-and-integration-mistakes).

## Testing

- Identify material success, failure, and recovery cases before behavioral changes. When unit or isolated tests are needed, write or update them before production logic. Existing valid coverage can satisfy unchanged cases; do not add tests for nonexistent behavior just to fill a checklist.
- For bug fixes, first reproduce through the closest practical user-facing path. If blocked, record the blocker and use the narrowest reliable reproduction. Verify the original failure after the fix, retaining or adding regression coverage capable of detecting it.
- Prefer E2E evidence for real UI/workflow and persistence boundaries through [verify-mural](.agents/skills/verify-mural/SKILL.md). Pair representative journeys with focused logic, storage, data, or host-runner checks for distinct risks. Exercise production code, not duplicated algorithms. Use challenging inputs relevant to the change; workflow length is not a measure of test quality.
- Select checks from changed contracts and risks. Broaden for affected shared behavior, integration boundaries, or unresolved failures, not automatically every layer or platform variant. Documentation/tooling work needs its relevant validation, not an app journey unless app behavior is affected. Do not run every data combination through slow UI automation when production-code assertions plus representative integration cover the same contract.
- Match evidence to the claim: screenshots for static appearance; bounded recordings with inspected frames for motion/transient defects; accessibility checks for names, roles, values and actions; acknowledged interaction outcomes; exact state after save/reopen for persistence. A build, tap exit code, accessibility frame or audio log alone cannot establish all these properties. Save repeatable evidence under `.build/verification/`; retain hardware and human-listening gaps explicitly.
- Correct invalid tests without losing their requirements. Preserve each distinct failure case through an appropriate replacement check, or report the evidence gap. Do not weaken valid assertions, remove failure coverage, or change requested behavior just to obtain a pass. Similar gestures can test different outcomes, such as changing versus reselecting or retaining across relaunch.
- Before running changed tests, confirm fixture suitability and target membership. Do not hand-edit generated project files. Update `scripts/generate_project.py` when needed and regenerate for Xcode configuration or non-synchronized source-membership changes, preserving the selected backend/signing recipe; regeneration is not a per-build ritual. Confirm intended test identities and counts actually ran; zero tests and required skips are not passes.
- Classify failures as app defects, incorrect expectations/measurements, unsuitable fixtures, or infrastructure problems before retrying. Start with the failing assertion, actual result and relevant code; inspect artifacts that resolve remaining uncertainty. Group related corrections and choose a rerun that can distinguish the proposed explanation. Model/resource faults retain the stricter physical-device stop rules above.
- Inspect affected visual checkpoints early. Include appearance, text size, screen size and motion variants where the change can affect them. Keep target-driven scrolling, meaningful UI-state waits and bounded entrypoints/progress logs. Do not repeat unchanged gestures/reboots without new evidence, disable synchronization, or blindly widen timeouts to manufacture a pass; use a supported alternative with independent readback or report the blocker.
- Measure build, startup, tests and cleanup together; distinguish reduced scope from faster identical coverage. Reuse evidence only while relevant production/test/fixture code, configuration, runtime, profile and exercised state remain applicable. Report passed, failed, blocked and unverified checks separately. Stop when the requested outcomes have sufficient current evidence, not after unrelated checks.

Only push when the user authorizes it, and distinguish a source/research checkpoint from production qualification.
